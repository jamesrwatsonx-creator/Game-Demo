### D-001 — Engine/stack: TypeScript + Three.js (web/WebGL) instead of Unity/C#
- **Phase:** Pre-build, before any implementation (Gauntlet section 2/12 toolchain evaluation).
- **Decision:** Build the prototype as a TypeScript web app (Vite + Three.js for rendering, Vitest for deterministic logic tests, Playwright/Chromium for input-latency and visual instrumentation), packaged for mobile via a WebGL/Capacitor-style wrapper path rather than a Unity Editor project.
- **Alternatives considered:** (1) Unity LTS + C# as specified by the prompt's default candidate stack. (2) Native Swift/Kotlin dual codebase (rejected immediately — doubles implementation cost, no shared deterministic sim, explicitly discouraged by "reject premature optimization"/minimum-dependency guidance, and this environment can't compile either).
- **Evidence available at the time:** OBSERVABLE — this execution container has Node 22 + npm/npx and a pre-installed Playwright/Chromium browser (`/opt/pw-browsers`), confirmed via `which`/`ls`. OBSERVABLE — no `unity`/`Unity` binary, no Android SDK, no Xcode/macOS toolchain is present or installable in this container (Linux, no GUI, no multi-GB Editor download path, no license flow). The Gauntlet prompt itself anticipates this: "Actual Unity compilation, rendering, device testing... require the corresponding tooling to be installed and accessible in the execution environment... Do not confuse the coding agent's ability to write the project with the availability of the native platform toolchain."
- **Relevant constraints / hypotheses:** Directly determines feasibility of section 14's Evaluation Harness (10,000-run survivability sim, reaction-window audit, input-responsiveness measurement, session simulation, camera-readability checks) and section 21's Hard Gates, all of which require *actually running* the simulation and renderer inside this session, headlessly and repeatedly.
- **Why this option won:** The prompt's own override clause names exactly four criteria for deviating from Unity: iteration speed, deterministic simulation, mobile performance, and testing. Given this container: (a) *Iteration speed* — Vite hot-reload and CLI-only workflow need no Editor GUI, which doesn't exist here; Unity Editor batch-mode would need an install this environment cannot perform. (b) *Deterministic simulation* — a fixed-timestep JS/TS update loop over a seeded PRNG (mulberry32) is as deterministic as Unity's approach and avoids importing a physics engine's own nondeterminism, satisfying the architecture contract's "prefer deterministic integer/fixed-step gameplay" without extra dependency. (c) *Mobile performance* — a low-poly instanced-mesh WebGL scene run through a real Chromium engine is genuinely profileable here (frame timing via `performance.now()`, draw-call counts via Three.js renderer.info); a Unity build cannot be produced or profiled at all in this container. (d) *Testing* — Vitest gives real headless logic tests now; Unity Test Framework requires Editor batch mode, unavailable here. All four override criteria are satisfied concretely, not speculatively, because they were checked against this actual environment rather than argued in the abstract.
- **Confidence:** High for *this environment*. Explicitly NOT a general claim that web beats Unity for this genre — see falsifier.
- **What would reverse it:** If a session gains access to an installed Unity Editor + Android/iOS SDKs, the deterministic-sim/render/input separation this build uses ports directly to a Unity project (same architecture contract), so the falsifying condition is "Unity tooling becomes available AND profiling shows the web build cannot hit stable 60fps on representative mid-tier mobile hardware where a Unity build could." That comparison cannot be run in this container and is recorded as an open gap (see GAPS.md).
- **Expected consequence:** Full core-loop prototype buildable, runnable, and automatically testable end-to-end inside this session; native `.ipa`/`.apk` artifacts are NOT produced here — packaging into Capacitor iOS/Android shells is prepared but the final compile/sign step needs Xcode/Android Studio outside this container, same limitation the prompt already accepts for Unity.
- **Observed consequence:** Full core sim + evaluation harness built and run entirely inside this session (Vitest, headless). 10,000-seed survivability sweep, reaction-window audit (20,177 samples), and AI-vs-AI session simulator all executed and passed/tuned using real measured output from this container. Zero native `.ipa`/`.apk` produced, as anticipated.
- **Later assessment:** validated (for this environment's constraints; general Unity-vs-web comparison remains untested — see GAPS.md).

### D-002 — Structural (not statistical) fairness: row-gap strictly exceeds every action duration
- **Phase:** Core simulation build.
- **Decision:** Row spacing is generated using the *player's actual current speed* at generation time (not a static formula), targeting a minimum time gap (`MIN_ROW_TIME_GAP_S = 0.9s`) with a `ROW_GAP_SAFETY_MARGIN = 1.12` to absorb within-chunk speed drift, and this gap is asserted (`ROW_GAP_EXCEEDS_ACTIONS` in constants.ts) to exceed every single-action duration (jump 0.5s, duck 0.4s, lane-change 0.18s). Combined with a hard cap of at most one "rail" (lane-change-only) cell per row, this makes INV-02 ("no unavoidable death without a prior losing decision") a property the generator satisfies *by construction*, for any lane count ≥ 2 (pigeonhole argument in course.ts docstring), not something verified only by sampling.
- **Alternatives considered:** Generate freely and filter/reject unfair rows post-hoc (statistical approach). Rejected: more expensive, harder to reason about, and doesn't generalize automatically to a lane-count change (CL-01's 4-lane falsifier) the way the algebraic proof does.
- **Evidence available at the time:** DERIVABLE — the reachability argument is pure combinatorics once "at most one rail lane" and "gap > every action duration" are fixed.
- **Relevant constraints / hypotheses:** INV-02, H-02, CL-01.
- **Why this option won:** A structural guarantee is falsifiable by a single implementation bug (which is exactly what the empirical sweep is for) but not by adversarial seeds — it doesn't degrade as difficulty/seed count grows, unlike a filtered/statistical approach whose false-negative rate is seed-count-dependent.
- **Confidence:** High, now empirically checked (see observed consequence).
- **What would reverse it:** A gameplay requirement that needs a hazard type reachability can't cover under this scheme (e.g. multi-lane simultaneous hard barriers) would require re-deriving the proof or reintroducing filtering.
- **Expected consequence:** Zero unavoidable-death detections across a large seed sweep.
- **Observed consequence:** Construction immediately surfaced two *implementation* bugs the proof itself doesn't prevent — the proof constrains the generator, not the AI/solver logic that must actually execute a rescue: (1) the AI reacted only to the obstacle in its *current* lane, not the lane it was about to dodge into, so a rail-dodge into a lane that itself needed a jump/duck silently dropped the second requirement; (2) with an unbounded ("omniscient") reaction budget, jump/duck were triggered the instant a row became "next," which for rows more than one action-duration away meant landing back on the ground *before* actually reaching the hazard — jumping too early doesn't clear a hurdle that hasn't arrived yet. Both fixed (see WORK-LOG.md WL-01/WL-02). After both fixes, the 10,000-seed sweep (both fast 300-seed and full 10,000-seed variants) passed with zero violations, and a 200-seed/20,177-row-crossing reaction-window audit found zero crossings under the hard physical floor.
- **Later assessment:** validated — but only after two rounds of empirical correction. The proof was correct about the *generator*; it said nothing about whether the *agent executing the rescue* was implemented correctly, which is exactly the gap the required empirical survivability test (section 14) exists to catch. Direct evidence that structural derivation and empirical testing are complementary, not substitutes for each other, in this codebase.

### D-003 — Tier-scaled AI "mistake chance" to bring AI-vs-AI session length into a short-session range
- **Phase:** Evaluation harness (session simulator).
- **Decision:** The bounded-reaction gameplay AI (not the fairness solver) now has a small, deterministic, per-row chance of skipping its reaction entirely — `AI_BASE_MISTAKE_CHANCE = 0.05` plus `0.02` per complexity tier — derived from a stable hash of the row index (not the mutable RNG stream), so it's reproducible without adding AI memory. Explicitly gated off when `reactBudgetS` is `Infinity` (the fairness-solver path), so it can never leak into the survivability proof.
- **Alternatives considered:** (1) Shrink `AI_REACT_BUDGET_S` closer to the hard floor — analyzed and rejected: since the AI's execution is deterministic once triggered (fixed-step sim, no missed frames), a smaller budget mostly changes *when* it reacts, not *whether* it succeeds, so it wouldn't meaningfully raise the error rate. (2) Increase raw speed escalation — rejected: row-time-gap is deliberately speed-invariant by design (D-002), so raw speed alone doesn't tax a purely time-based reactive agent at all. (3) Add explicit "combo rows" (adjacent rows forcing rapid jump-then-duck) — deferred as higher implementation risk for the remaining build budget; noted as a follow-up in GAPS.md.
- **Evidence available at the time:** OBSERVABLE — first AI-vs-AI session-simulation run (200 seeds, gameplay-budget AI on both sides, once the harness itself was fixed to actually drive both players — see WORK-LOG.md WL-03) measured a 86.0s median session, 6.8-97.7s p10-p90, against the spec's explicit "short sessions" target.
- **Relevant constraints / hypotheses:** Section 15 experience gate ("short sessions"); tension with INV-02/D-002's generous fairness margins.
- **Why this option won:** It's the only lever that increases genuine error rate without eroding the structural fairness guarantee — mistakes are attributed to attention/execution, not to the course becoming unsolvable.
- **Confidence:** Medium — tuned against one measurement pass in this session, not against human playtesting. The resulting distribution (median 33.7s, p10 7.7s, p90 35.7s) is a plausible short-session shape but the p90≈median clustering (vs. a more natural long tail) is flagged as unexplained and worth a follow-up look, not asserted as correct.
- **What would reverse it:** Human playtesting showing sessions still feel too easy/long, or too punishing/short, at either end of the distribution.
- **Expected consequence:** Median AI-vs-AI session materially shorter than 86s, closer to typical short-session mobile-arcade pacing (no specific benchmark figure available to target precisely — see EXPERIMENT.md).
- **Observed consequence:** Re-run after the change: median 33.7s, p10 7.7s, p90 35.7s, 0/200 sessions failed to end, average 12.97 near-misses per session (up from 0.83 — also fixed by the harness correction in WL-03, not by this change alone). 10,000-seed fairness sweep re-confirmed clean after this change, proving the gate correctly excludes the solver path.
- **Later assessment:** unresolved — plausible and evidence-backed for this session, but explicitly a tuning choice pending human validation, not a proven-optimal pacing curve.

### D-004 — Camera/presentation model: Mirrored (linked worlds) chosen over literal Head-On, resolving CL-03/CL-07/H-01
- **Phase:** Rendering build, after both modes were implemented and screenshotted at matched difficulty tiers (base tier ~34km/h/32-41m, and top tier 94km/h/~1450m — the latter reached via a dedicated debug fast-forward using the omniscient solver on both sides, see WL-06/WL-07).
- **Decision:** Ship with `cameraMode = "mirrored"` as the default: a portrait top/bottom split-screen where each half is an independent, ordinary third-person chase camera on one runner's own track (opponent on top, player on bottom, larger share of the frame). "Head-On" (both tracks rendered into one shared lane corridor via a bounded modulo-wrap of each player's own unbounded z — see `HEAD_ON_ARENA_LENGTH_M`/`wrapZ` in constants.ts/camera.ts) is retained as a togglable secondary mode, not the default.
- **Alternatives considered:** Literal head-on as default (the framing named first in the original prompt); a from-scratch third presentation model (rejected — the prompt only asks for a comparison between these two, and no evidence surfaced during the build suggesting a third model was needed).
- **Evidence available at the time:** OBSERVABLE, from actual screenshots (test-results/camera-*.png, captured by tests/e2e/smoke.spec.ts), not just reasoning: at the base tier, both modes were legible. At the top speed/complexity tier, the head-on view's shared lane corridor visually overlaps both players' independently-generated obstacles at different depths into the same 3-lane space — the screenshot shows a dense, ambiguous stack of red/blue/orange geometry where it is genuinely hard to attribute which obstacle belongs to which player's track. The mirrored view keeps both halves independently legible at the same tier because each half only ever renders its own player's obstacles.
- **Relevant constraints / hypotheses:** Directly resolves CL-03 (derivable concern: head-on becomes unreadable at higher closing speed), CL-07 (open hypothesis: does mirrored communicate competitive interaction more clearly), H-01 (mirrored stays readable at higher tiers than head-on).
- **Why this option won:** The failure mode observed was not exactly what CL-03 predicted (foreshortening from combined closing speed) — it was corridor-sharing causing cross-player obstacle overlap, a compositional/legibility problem inherent to rendering two independently-fair-but-uncoordinated procedural streams into one shared visual lane space. Different mechanism, same practical conclusion: **CL-03 is supported, but for a different causal reason than originally hypothesized** — worth preserving precisely rather than claiming the original mechanism was confirmed (see EPISTEMIC-STATE.md).
- **Confidence:** Medium-High for *this implementation's* head-on approach specifically. Does not rule out that a differently-engineered head-on camera (e.g., visually offsetting the two corridors side-by-side instead of overlapping them, or dynamic zoom) could resolve the overlap problem — that variant was not built or tested; noted as a follow-up in GAPS.md rather than assumed impossible.
- **What would reverse it:** A head-on variant that separates the two players' geometry (e.g., parallel offset lanes converging visually without literal overlap) passing the same screenshot comparison at the top tier.
- **Expected consequence:** Mirrored is the default a first-time player sees; head-on remains available (HUD toggle) for players who prefer it or for future experimentation, but is not asserted as equally readable.
- **Observed consequence:** Screenshots captured for both modes at both tiers (see test-results/); mirrored legible at all tiers tested, head-on legible at the base tier only.
- **Later assessment:** validated by this session's available evidence; not validated by human testers (see G-01).
